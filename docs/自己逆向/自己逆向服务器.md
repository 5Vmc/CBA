# 自己逆向服务器

## 目标

在没有原服务端代码的前提下，先做一套“能驱动现有客户端跑起来”的兼容服务器，而不是一开始追求完整复刻测试服。

这件事是可行的，因为当前客户端已经把这三类关键信息暴露出来了：

- 协议入口：`E:\UGit\CBA_Card\bigBangClient\Assets\Scripts\GameConst\ProcID.cs`
- 发包调用：`E:\UGit\CBA_Card\bigBangClient\Assets\Scripts\GameManager\NetworkManager.cs`
- protobuf 结构：`E:\UGit\CBA_Card\bigBangClient\Assets\Scripts\Protos`

## 当前客户端能反推到什么程度

可以较高置信度反推出来的内容：

- 请求方法名，例如 `cs_login`、`cs_fetchAllPlayers`、`cs_enterGame`
- 请求/响应/通知的 protobuf 类型
- 登录后主流程需要的返回时序
- 球员、背包、资源等模块的主要字段
- 大量服务端通知名称，例如 `sc_updateCardInfo`

不能直接完整反推的内容：

- 运营侧真实规则
- 活动和排行榜判定
- 反作弊、限流、封禁逻辑
- 战斗裁定与帧同步细节
- 线上数据库结构和后台工具链

结论：

- 做一套“兼容当前客户端”的私服是现实的
- 做一套“与原测试服无差别”的服务端，单靠客户端代码不现实

## 现有客户端网络结构

客户端不是单一接口，而是两段式：

1. HTTP 启动层  
   先拿选服信息和服务器地址。

2. TCP 游戏层  
   再走自定义封包 + protobuf 进行登录、进服、养成、战斗等业务。

### HTTP 启动层

代码入口在：

- `E:\UGit\CBA_Card\bigBangClient\Assets\Scripts\GameConst\ServerConst.cs`

已经能确认的接口：

- `SERVER_SELECTOR_URL = {SERVER_HOST}/cba/server_selector.php`
- `SERVER_LIST_URL = {SERVER_HOST}/cba/server_list.php`
- `PVP_BATTLE_URL = {SERVER_BATTLE_HOST}/cba/get_pvp_battle.php`

当前开发默认服常量还是：

- `ServerHostTest = http://47.99.113.240`

### TCP 游戏层

代码入口在：

- `E:\UGit\CBA_Card\bigBangClient\Assets\Babu\Scripts\Basic\Net\Socket\SocketOperate.cs`
- `E:\UGit\CBA_Card\bigBangClient\Assets\Babu\Scripts\Basic\Net\Socket\ServerNotificationCenter.cs`

已确认特点：

- 应用层 envelope 使用 `MessagePack`
- envelope 本体是 3 元结构：`sessionId`、`methodName`、`protobuf bytes`
- `sessionId == 0` 时客户端把消息当成服务端主动通知
- `sessionId != 0` 时客户端走请求回调链路

### 已确认的协议细节

基于实际抓包，已经确认：

1. 客户端请求头是 `2` 字节长度前缀
2. 服务端响应头是 `4` 字节长度前缀
3. 客户端请求体是 MessagePack 三元数组
4. 服务端响应体不是数组，而是顺序写入：
   `sessionId` -> `methodName` -> `payload`
5. 普通 response 的 `methodName` 为空串
6. notify 的 `methodName` 才是类似 `sc_updatePlayerInfo` 的名字

抓到的关键真实连接是：

- `47.99.113.240:10001`

这已经可以作为第一版兼容服的 TCP 目标参考。

## 建议技术栈

第一版最省事的是：

- 服务端语言：`C# / .NET 8`
- 数据库：`SQLite`
- 后续扩展：`PostgreSQL`

原因：

- 可以直接复用客户端现成的 protobuf C# 文件
- 不需要先从 C# 反推出 `.proto`
- 对 MessagePack 和 TCP socket 处理都比较直接

## 一步步实现路线

### 第一步：先让客户端不连远端测试服

目标不是先写业务，而是先把流量导向你自己的地址。

要做的事：

1. 搭一个本地 HTTP 服务
2. 让客户端的 `server_selector.php` 和 `server_list.php` 指向你自己的 HTTP
3. 让这个 HTTP 返回你自己的 TCP 游戏服地址

### 第二步：先实现 HTTP 启动层

最少要有：

1. `GET /cba/server_selector.php`
2. `GET /cba/server_list.php`

建议做法：

1. 先用当前骨架返回最简单 JSON
2. 再抓真实测试服返回结果
3. 对比客户端解析逻辑，逐步把字段补齐

### 第三步：继续校准 TCP 封包协议

这个阶段只做协议验证，不做复杂业务。

要确认的点：

1. 长度前缀字节数
2. 大小端
3. MessagePack envelope 结构
4. 请求回包时是否要回相同 `methodName`

建议做法：

1. 连一次远程测试服
2. 抓登录前几条 TCP 包
3. 对照 `SocketOperate.cs` 验证剩余的 body 细节

当前已经不再需要验证“2 字节还是 4 字节”，这个结论已经落地到 `MyServer` 骨架里了。

### 第四步：实现最小登录链路

1. `cs_login`
2. `cs_fetchAllPlayers`

## 当前已经落地的服务端骨架说明

已经创建的目录：

- `E:\UGit\CBA_Card\MyServer\src\CbaCompatServer`

当前已经做了什么：

- 一个 `ASP.NET Core` HTTP 服务
- 一个 TCP `BackgroundService`
- MessagePack envelope 解码/编码
- 内存态账号与角色数据
- 最小登录链路 handler
- `EnterGame` 后首批 4 个 notify

当前还没做什么：

- `SQLite` 持久化
- 更完整的 HTTP 选服 JSON 对齐
- 真正的错误码体系
- 复杂 notify 补齐
- 战斗、邮件、任务、商城

## 推荐的下一步实施顺序

1. 再抓一次更完整的真实 TCP 登录流量，确认更多业务包
2. 抓一次真实 `server_selector.php` / `server_list.php` 返回
3. 用当前 `MyServer` 骨架跑起来
4. 把 Unity 客户端切到本机 HTTP
5. 跑通 `login -> fetch players -> create player -> enter game`
6. 记录进入主界面后缺哪些 notify / 接口
7. 逐个补模块

## 最后结论

不要“先复刻原服”，而要“先做最小兼容服务器”。  
只要登录链路和进入主页的数据模块跑通，后面的工作就会从“猜协议”变成“补业务”，难度会下降很多。
